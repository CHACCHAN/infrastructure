# ネットワーク設計

## 決定済み

### VLAN

サーバーネットワークは `172.20.0.0/16` を、VLANごとの `/24` に分ける。ゲートウェイは各 `/24` の `.254`。VLAN間の通信はルータで制御する。

| VLAN | サブネット | 用途 |
| --- | --- | --- |
| 20 | `172.20.20.0/24` | Proxmox ノード |
| 21 | `172.20.21.0/24` | k3s ノード |
| 22 | `172.20.22.0/24` | Private(開発専用機など) |
| 23 | `172.20.23.0/24` | 基幹システム(物理PBS、TrueNAS。移行後に接続) |
| 24 | `172.20.24.0/24` | Hermes Agent(AI専用) |

### ID・VMID・IP

IDひとつから、VMIDとIPを決める。

```text
VMID = VLAN × 100 + ID
IP   = 172.20.<VLAN>.<ID>
```

- ID は 1〜99 の整数で、VLANの中で一意。YAML には先頭の0を付けずに書く(`08` は文字列、`010` は8進数として読まれる)。物理機と仮想機は同じID空間を共有する(物理機にはVMIDがない)。
- 例: VLAN21 の ID 1 → VMID `2101` → `172.20.21.1`。
- ホストは、グループの `vlan`、自分の `id`、配置先の `node` だけを宣言し、VMID・IP・ゲートウェイ・VLANタグは導出する。
- 複数のNICを持つホストの VMID は、主となるNICのVLANで決める。

予約済みのID:

| VLAN | ID | 用途 |
| --- | --- | --- |
| 21 | 5 | Ingress の VIP(`172.20.21.5`) |
| 21 | 6 | k3s API の VIP(`172.20.21.6`) |

### 物理構成

- Proxmox ノードは、各ノードに 1GbE のNICが2つある(ノードの詳細は [hardware.md](hardware.md))。
- 構成: `WAN → ER605 → SWHUB → Proxmox ノード(NIC1)`、`SWHUB2 → Proxmox ノード(NIC2)`。SWHUB は 802.1Q のタグVLANに対応している。SWHUB2 は NIC2 側の機器(Proxmox ノード。PBS、TrueNAS は移行後)だけをつなぎ、ER605 や SWHUB にはつながない。
- NIC1: SWHUB(VLAN対応)につなぐ。Linux の VLAN サブインターフェースでVLANを分け、VLANごとに `vmbr` を作ってVMへ渡す。
- NIC2: VLAN非対応の SWHUB2 へつなぐ。PBS と TrueNAS は、移行後に同じスイッチにつなぐ。クラスタ・バックアップ・ストレージの通信用で、ゲートウェイはなく、ルーティングしない。SWHUB2 はVLAN非対応なので、NIC2側のVLAN分離は各ホストの設定によるもので、スイッチは強制しない。
- NIC2 側の Proxmox ホスト用ネットワークは `10.20.20.0/24`(VLAN20 のタグ付き、ブリッジ `vmbr220`)。pve01 は `10.20.20.1`。
- PBS は物理マシンに直接入れる(VLAN23)。Proxmox ノードではなく、PBS 専用機にする。接続は移行後。
- ルータは TP-Link ER605。VLANのタグ付けとVLAN間ルーティングを担う。
- 自宅LANは `192.168.68.0/24` で、ラボの `172.20.0.0/16` と重ならない。
- リアルタイム通信は Cloudflare のサービスを使う。外部からの直接UDPの受け口は要らない。

### Proxmox クラスタ

- Proxmox の HA は使わない。k3s が自力で冗長化するため。corosync が落ちても、動作中のVMは止まらない。
- corosync は2リンクにする。第1リンクを NIC2、第2リンクを NIC1(VLAN20)にして、どちらかが落ちても knet が切り替える。
- NIC2 には、移行後に PBS・TrueNAS もつなぐ。そのときは、バックアップの転送に帯域の上限(`bwlimit`)を設け、corosync のレイテンシを守る。

### ノートPC(pve02・pve03)のNIC

- NIC1 は内蔵LAN、NIC2 は USB LAN にする。USB LAN は、人が触れて抜けない場所に設置する。

### 移行

- 旧構成は、移行中も止めない。新構成へ段階的に移す。
- TrueNAS と PBS は、移行が進んでから接続する。それまで、新構成の設計・実装の対象に含めない。
- 新構成は、pve01 と k3s01 だけで先に構築する。旧構成のアプリを新構成へ移したあとで、旧構成の物理マシンを Proxmox ノードとして参加させ、k3s02・k3s03 を作る。

### 名前解決

- 名前解決は Cloudflare の DNS を使う。
- ルータの構成が固まってから、詳細を設計する。

### リモートアクセス・公開

- リモートアクセスは `cloudflared` を使う。
- 管理UI(Proxmox・PBS・TrueNAS)は LAN 内だけで使う。Cloudflare Tunnel には載せない。

## 未決

- NIC2側の分割。クラスタ/バックアップ用(VLAN30)と、ストレージ用(VLAN31)に分けるか。k3s ノードは NIC2 に載せない([k3s.md](k3s.md))。
- ER605 の上流の構成(ER605 の上にあるルータの有無)と、自宅LAN(`192.168.68.0/24`)がどの機器にぶら下がっているか。
- VLAN間のFWポリシー(特にHermes帯域の隔離、ラボから自宅LANへの通信の遮断)。ER605 のACLの機能(単体モードか Omada コントローラ)に依存する。
- ER605 と SWHUB のトランクが1本なので、VLAN間の通信はこの1本を通る。帯域が足りなければ、リンクアグリゲーションか L3 スイッチを検討する。
- 自宅LANからラボへの到達性。管理UIとTraefik(`172.20.21.5`)を自宅のPCから使うかどうかで決まる。
- Proxmox クラスタの定数(4台は偶数のため)。PBS の接続後に、PBS 機へ QDevice を置く案がある。
- 追加のVLAN(DMZ、テンプレート/一時用)。
- 名前解決の細部(LAN内クライアントの問い合わせ先、ノード同士の名前解決、プライベートIPを返す応答を拒否するDNSリバインド対策への対処)。
- `cloudflared` で届かせる範囲。
